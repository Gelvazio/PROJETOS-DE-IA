- Cada pasta é um **clone completo** do mesmo remoto `main`, com `.git` próprio. Não existe "clone oficial".
- **O problema real não é divergência (hoje é zero), é concorrência de push:** todas apontam para a
  mesma `main`. Se duas sessões commitarem em clones diferentes e a segunda empurrar depois, o push é
  recusado (`non-fast-forward`); o `git pull --rebase` resolve, mas se as duas mexeram no mesmo
  `tasks/STATUS.md` o conflito é garantido.
- O `rules-ai` já tem a ferramenta certa: `scripts/UPDATE.py` (tarefa **UPDATE-REPOS**, etapa 021,
  aberta com 13 subtarefas LEVE livres). Ele roda `git fetch` + `git pull --rebase --autostash` em
  cada pasta e **nunca** faz push/merge/force; se o rebase parar, deixa o conflito para a sessão.
- O portal usa os docs da pasta `aulas-senai-CLAUDE-OPUS-LIDER`; a skill
  `gerenciador-de-tarefas` é o fluxo do líder.

### Opções

**A — Manter as 14 pastas e disciplinar a sincronização (recomendada no curto prazo).**
- Antes de trabalhar num clone: `python C:\fontes\rules-ai\scripts\UPDATE.py --pasta <nome>`.
- Ao terminar: commit na `main` do clone, `python ...UPDATE.py --pasta <nome>` de novo e `git push`.
- Regra de convivência: **uma sessão por repositório por vez** para edição de quadro (ou aceitar resolver
  conflito do `STATUS.md` na mão).
- Custo: zero mudança estrutural. Risco: conflito ocasional de quadro quando duas contas rodarem juntas.

**B — Eleger um clone de referência por repositório.**
- Aulas: `aulasenai`; dashboards: `dashboard-ai-codex`.
- Só o clone de referência commita quadro e faz push; os demais são atualizados pelo `UPDATE.py`
  (pull) e entregam trabalho por commit local + aviso ao líder, que reaplica no clone de referência.
- Custo: muda o fluxo de todas as IAs; exige o líder como intermediário. Risco: trabalho dos clones
  pode ficar parado esperando o líder.

**C — Reduzir a 1 pasta por repositório** (`aulasenai` + `dashboard-ai-codex`) e arquivar as outras 12
(fora do Git, numa pasta de backup).
- Elimina o problema pela raiz; libera ~5 GB se somar os `.git` duplicados.
- Custo alto: quebra o fluxo "uma pasta por modelo/conta", o portal (lê `OPUS-LIDER`) e o hábito atual.
  Reversível, mas exige recriar clones depois.

**D — Branch por sessão** (`sessao/<ia>` em cada clone): resolve conflito, mas **viola** a regra
"tudo na `main`" (`git-geral.md`). Não recomendo.
**E — `git worktree`** (um repo e N pastas de trabalho): é exatamente o problema que o worktree
resolveria, mas **viola** a regra "sem git worktree" da raiz. Não recomendo sem mudar a regra.

### Recomendação

contas for frequente, migrar para **B** depois — B preserva as pastas e o portal.
